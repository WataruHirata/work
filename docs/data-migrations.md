# データベース変更・データ移行方針

## スキーママイグレーション

初期実装はSupabase PostgreSQLとSupabase CLIを採用する。スキーマは `supabase/migrations/` に追加し、ローカルSupabaseへ全マイグレーションを適用・LintするCIを通す。Production workflowは、保護されたGitHub `production` environmentから全CI成功後にのみ `supabase db push --linked` を実行する。DB製品・運用の最終承認、バックアップ、復旧目標が確定するまで本番適用を有効化しない。

- すべてのスキーマ変更はレビュー可能なコードとして記録し、手作業の本番変更を禁止する。
- データ量、ロック、処理時間、互換性を評価する。大規模・破壊的変更はexpand/contract等で段階化し、旧版と新版の共存期間を定める。
- カラム削除・型変更・制約強化は、利用コードの切替と本番データの適合確認後に別リリースで行う。
- データ変換は再実行可能性、進捗・件数・エラー記録、部分失敗時の復旧方法を明記する。
- リリース前に適用順序、バックアップ状態、ロールバック可否、担当者、停止・告知条件を確認する。DB変更のロールバックが安全でない場合は、前方修正またはバックアップ復元を明示する。
- Productionマイグレーションは段階的・後方互換の追加変更を原則とし、破壊的操作はexpand/contractと別途承認の後に実施する。

## 初期データ移行

要件書が候補としている商品、店舗、利用者・権限、通常売価、特売、店舗別商品、売上履歴について、対象と期間をデータオーナーが承認してから移行する。

1. 抽出元、所有者、対象期間、スナップショット時点、件数を確定する。
2. 個人情報と秘密情報の取扱いを承認し、必要に応じて匿名化した非本番データを作成する。
3. データプロファイリングとコード・欠損・重複・有効期間のクレンジングを行い、除外と補正を記録する。
4. 変換規則を版管理し、テスト移行を複数回行う。
5. 件数に加え、店舗・営業日別売上、税額、返品・取消、価格有効期間、所属・権限を照合する。許容差異と承認者を事前に決める。
6. 本番切替手順、変更凍結、最終差分、照合、受入、差戻し判断時刻をリハーサルする。
7. 移行結果・例外・承認を保管し、移行後も業務責任者がサンプルと集計を確認する。

## リリースと切戻し

移行とアプリケーションを一体のリリース計画で扱う。先行10店舗では、新旧結果の照合、切替条件、二重入力を避ける手順、切戻し時のデータ差分の扱いを確定する。保存期間、バックアップ方式、復旧目標と復元試験が承認されるまで、本番移行日を確定しない。
