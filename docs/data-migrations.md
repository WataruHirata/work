# データベース変更・データ移行方針

## スキーママイグレーション

### 開発環境の起動前自動適用（AT-10/12）

`npm run dev` の `predev` が `scripts/migrate.mjs --auto` を実行する。`AUTO_MIGRATE=true` の場合のみ、Supabase CLI 2.121.0 の `db push --linked --yes` により未適用の版管理SQLを適用する。初回のみCLIをnpxで取得する。`DEV_SUPABASE_PROJECT_REF`、アプリのSupabase URL、`supabase/.temp/project-ref` の3点が一致することを事前検査する。未リンク・不一致・適用失敗ではサーバーを起動しない。新しい環境の既定値は自動適用無効。APIリクエストや本番ビルドではこの処理を呼ばない。

`npm run db:migrate:check` はdry-run、`npm run db:migrate` は手動実行。CLI認証とリンクは事前に必要。DBパスワードが必要な環境では `SUPABASE_DB_PASSWORD` をサーバー側の環境変数として設定する。秘密情報はログに転記しない。本番/CIからの開発コマンド実行は拒否し、本番は既存の保護されたproduction workflowでCI・レビュー後に適用する。

前進は新規SQLの追加と再起動で行い、適用済みSQLを編集しない。失敗時は原因を修正して再実行する。reset・履歴repair・データ削除を自動実行しない。切戻しは既存方針どおり前方修正またはデータを保持したアプリ差戻しとする。`tests/migration-policy.test.ts` は明示的な有効化、対象不一致、本番/CI拒否を検証する。

接続実装では `202610210001` 以降に、店舗端末/在庫/連携キュー/ユーザー属性、原子的な標準売上取込、初回パスワード変更の強制、下書き編集と公開時検査、端末秘密情報を除外する監査、通常売価版を追加した。取込履歴の一意性は「ファイル×店舗」から「ファイル×店舗×営業日」へ拡張する。既存テーブル/データを削除しない。PGliteで前進適用と権限・件数・金額・再送を検証するが、実Supabase CLI適用・並列動作・復旧試験は別途必要。切戻しは追加データを保持してアプリを戻すか前方修正とし、登録済みデータを削除する逆マイグレーションを自動実行しない。

`202610220004` は、発注者を有効なログイン利用者へ拡張し、発注ヘッダ・金額付き明細・基幹連携ジョブを同一トランザクションで作成する。既存発注は変更しない。適用後は発注用ロールを持たない有効利用者による発注、無効利用者の拒否、金額一致、同一要求の冪等性、連携結果による状態更新を照合する。切戻しは既存データを保持した前方修正またはアプリ差戻しとする。

初期実装はSupabase PostgreSQLとSupabase CLIを採用する。スキーマは `supabase/migrations/` に追加し、ローカルSupabaseへ全マイグレーションを適用・LintするCIを通す。Production workflowは、保護されたGitHub `production` environmentから全CI成功後にのみ `supabase db push --linked` を実行する。DB製品・運用の最終承認、バックアップ、復旧目標が確定するまで本番適用を有効化しない。

- すべてのスキーマ変更はレビュー可能なコードとして記録し、手作業の本番変更を禁止する。
- データ量、ロック、処理時間、互換性を評価する。大規模・破壊的変更はexpand/contract等で段階化し、旧版と新版の共存期間を定める。
- カラム削除・型変更・制約強化は、利用コードの切替と本番データの適合確認後に別リリースで行う。
- データ変換は再実行可能性、進捗・件数・エラー記録、部分失敗時の復旧方法を明記する。
- リリース前に適用順序、バックアップ状態、ロールバック可否、担当者、停止・告知条件を確認する。DB変更のロールバックが安全でない場合は、前方修正またはバックアップ復元を明示する。
- Productionマイグレーションは段階的・後方互換の追加変更を原則とし、破壊的操作はexpand/contractと別途承認の後に実施する。

## 初期データ移行

`202610210005` は個人宛通知に修正依頼IDと重複防止インデックスを追加し、申請・承認の状態遷移で通知を生成する。既存の承認・金額更新RPCは変更しない。既存通知への依頼IDの遡及付与や過去依頼の一括通知は行わない。適用後、申請1件の一次/最終承認通知と店舗への結果通知を照合する。切戻し時も通知・依頼・承認履歴を残し、前方修正する。

### 本部変更指示の追加（202610210004）

`store_instructions`、`store_instruction_targets` とRLS/RPC/監査、既存特売公開の通知トリガーを追加する。既存売上・価格を変換しない。通知は指示発行時にトランザクション内で書き込み、既存特売への過去分の通知は生成しない。PGliteで全版の前進適用と対象・通知件数の照合を検証する。ステージングで指示1件・対象2店の通知と既存店舗端末の閲覧を照合してから段階展開する。

切戻しはアプリを前版に戻し、追加テーブルと監査・通知は保存する。発行済み指示と店舗確認の削除を伴うスキーマ逆適用は行わず、障害は前方マイグレーションで修正する。実SupabaseでのCLI適用・Lintと復旧リハーサルは別途必要。

要件書が候補としている商品、店舗、利用者・権限、通常売価、特売、店舗別商品、売上履歴について、対象と期間をデータオーナーが承認してから移行する。

1. 抽出元、所有者、対象期間、スナップショット時点、件数を確定する。
2. 個人情報と秘密情報の取扱いを承認し、必要に応じて匿名化した非本番データを作成する。
3. データプロファイリングとコード・欠損・重複・有効期間のクレンジングを行い、除外と補正を記録する。
4. 変換規則を版管理し、テスト移行を複数回行う。
5. 件数に加え、店舗・営業日別売上、税額、返品・取消、価格有効期間、所属・権限を照合する。許容差異と承認者を事前に決める。
6. 本番切替手順、変更凍結、最終差分、照合、受入、差戻し判断時刻をリハーサルする。
7. 移行結果・例外・承認を保管し、移行後も業務責任者がサンプルと集計を確認する。

## リリースと切戻し

移行とアプリケーションを一体のリリース計画で扱う。先行10店舗では、新旧結果の照合、切替条件、二重入力を避ける手順、切戻し時のデータ差分の扱いを確定する。保存期間、バックアップ方式、復旧目標と復元試験が承認されるまで、本番移行日を確定しない。

## 202610220001: 特売公開時の変更依頼

テーブル追加・既存データの更新はなく、`notify_campaign_publication` の処理を、商品/価格/開始・終了日時付きの作業指示と店舗お知らせの同時保存へ置き換える。PostgreSQLの通常の版管理マイグレーションで前進適用する。切戻しは前方修正マイグレーションで直前版の同関数へ戻す。すでに発行した依頼・店舗確認・監査は削除しない。既存公開済みデータの再通知はしない。新関数の適用・対象店と非対象店・複数商品・再更新時の通知重複防止は `tests/campaign-change-requests.test.ts` の隔離PGliteで検証する。本番適用はこの作業では実行していない。
