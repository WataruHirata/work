# システム設計方針

## 目的と前提

この文書は、要件書から導けるシステム境界と設計制約を記録する。技術スタック、配置先、DB、API・ファイルIFの物理仕様は未決定であり、承認済み設計判断なしに固定しない。

## システム境界

- 対象: POS売上のファイル取込、店舗別営業日判定、監視・再取込、集計、日次締め、修正・承認、マスタ、特売、権限、監査、出力。
- 既存POS・基幹システムは原則維持する。
- 在庫は基幹からの連携値を参照する。発注入力以降の承認・基幹転送・結果・納品確認は未確定で、確定したスコープのみ実装する。
- 店舗情報サイトの連携は詳細とIFが確定するまで設計対象の境界に留める。
- POS連携は深夜の日次ファイルが前提。リアルタイム処理を前提としたUXや業務判定を設計しない。

## 論理コンポーネント

1. **業務UI**: 権限別ポータル、売上確認・締め・修正、承認、商品・特売・店舗管理、在庫・発注（承認範囲内）、通知、監査検索。
2. **業務サービス**: 営業日判定、集計、状態遷移、金額・税計算、ロールとデータ範囲の認可。
3. **連携処理**: POS・基幹等のアダプター、形式検査、重複制御、再処理、結果履歴、通知。
4. **永続化**: 業務データ、マスタ、有効期間、監査ログ、連携・バッチ履歴。データモデル確定後に物理方式を決める。
5. **運用・監視**: 取込状況、バッチ結果、失敗再処理、バックアップ、障害連絡、監査可能性。

具体的なサービス分割や配置方式は、負荷・可用性・チーム体制とコストを比較したADRを承認して決める。

## 重要な業務不変条件

- 売上の営業日帰属は店舗ごとの締め時刻と境界設定で決める。標準・24時間・モール・駅前店舗の境界を試験する。
- 取込は同一データの再送・再処理で二重計上しない。元ファイル識別子と処理履歴の方式はPOS仕様確定後に決める。
- 締め当日、翌日以降の承認、月次確定後の変更不可という状態遷移と権限をサーバー側で強制する。
- 特売は一企画に複数商品・店舗を持ち、POS反映状態と店舗作業状態（値札/POP/売場表示）を商品・店舗単位で別管理する。通常売価とEDLP対象区分は既存情報を参照する前提で、新規マスタ化や自動価格連携は行わない。参照元・POS IF確定までは適格性未確認の特売を公開拒否する。
- 税率、端数、返品・取消は要件書と受入試験に基づき、一元化した業務ロジックで扱う。
- 金額・価格・締め・承認・返品等の監査記録は実行者、日時、操作、変更前後を保持する。

## 品質属性と設計入力

- 画面応答2秒、通常400～500人・繁忙時700人、半日以内復旧は提案または候補値である。測定条件、稼働率、RTO/RPOが合意されるまで最終SLOとして扱わない。
- 締めピーク（21:00～23:30）と深夜連携の競合を性能設計・試験に含める。
- 店舗・エリア・担当売場のデータ範囲を全てのAPI・出力・バックグラウンド処理で一貫して検査する。
- 共用PCでの利用を前提に、セッション・ログアウト・重要操作の個人識別を設計する。
- UIモーション・インフォグラフィックは [UI・モーション方針](./ui-motion.md) を適用する。

初期のアプリ/DB/配備ハーネスの実装範囲と、業務機能の段階別受入条件は [実装ロードマップ](./implementation-roadmap.md) を参照する。現在のダッシュボードは架空データのプレビューであり、ライブ運用機能とは区別する。
