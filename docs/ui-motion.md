# UI・アニメーション方針

## 共通UIの実装

全ページはNext.js App Router上のTypeScript / React（`.tsx`）で実装する。ページ名・ナビゲーション・ブランド・テーマのCSS変数（色、サイズ、フォント、モーション）・レスポンシブ設定は `src/config/ui.ts` を唯一の定義元とする。ルートレイアウトがテーマとメディアクエリを適用し、`globals.css` は共通クラスの構造と設定値の参照を担当する。メディアクエリ条件にはCSS変数を使用できないため、条件も同じ設定ファイルで管理する。

店舗/管理ポータル・業務ページ・管理機能ログインは共通サイドバーと `PageLayout` を使用する。店舗ポータル `/` は初期表示から店舗概況を表示し、機能メニュー・管理ログイン・共通メニューへの重複ボタンは本文に置かない。店舗5機能/管理10機能と入口認証は [ルート設計](./routes.md) に従う。業務データから決まるグラフの高さ・座標は各画面に残す。DB取得はServer Component、入力・状態更新はClient Componentで扱う。業務規則・権限はUI設定へ移さない。

店舗概況の表示例は当日売上・客数・客単価・7日間売上、日次推移、部門構成とする（FR-005/006、AT-03/10の表示基盤）。店舗識別が未実装の間は架空サンプルであることを明示し、実データ取得は追加しない。推移にはデータ表、構成比には部門名・金額・比率を併記する。

関連要件はFR-005 / FR-006（集計表示）、AT-03 / AT-10（表示・操作基盤）。設定参照の整合性を `src/config/ui.test.ts` で検証する。画面読み上げ・実ブラウザ操作・倍率変更は別途手動検証が必要。

### 業務画面の共通フォーマット

共通テーマは濃紺 `--accent-strong` を見出し・Primary操作、青 `--accent` をフォーカス・Secondary操作、`--text-subtle` を説明とメタ情報に使う。警告と成功は、それぞれ `--warning` / `--warning-soft`、`--success` / `--success-soft` の文字色と背景色を組み合わせ、色だけでなく状態ラベルも表示する。

新規画面は `ui-workspace` → `ui-section-stack` → `ui-card` / `ui-list` / `ui-detail` の順に組み立てる。操作列は `ui-actions`、ボタンは `ui-button-primary` / `ui-button-secondary`、状態は `ui-badge` と状態別クラス、結果通知は `ui-message-success` / `ui-message-warning` を使用する。既存の `page-panel`、`primary-button`、`ghost-button`、`badge`、`status` も同じトークンへ接続し、旧画面だけ別の見た目にならないようにする。

一覧画面は「検索条件 → サマリー → 一覧 → 詳細 → 操作」、詳細画面は「タイトル → メタ情報 → 説明 → 確認 → 実行」、更新フォームは「入力 → レビュー → 実行」の順序を基本とする。金額・承認・締めなどの高リスク操作では確認UIを省略しない。700px以下では主要Gridを1列にし、操作列のボタンを全幅にする。

## 体験目標

店舗の共用PC、PC操作に不慣れな利用者、売場の忙しい業務を前提に、短い操作で確実に業務を完了できるようにする。アニメーションは画面構造の理解、操作結果の伝達、売上などの数値の把握を助けるために積極的に使う。ただし、正確さ、操作速度、可読性、アクセシビリティを優先する。

## 動きを使う場所

- **画面遷移**: パネルの展開、タブ・フィルター変更、モーダルの出入りに短いトランジションを使い、画面上の位置関係を保つ。
- **操作フィードバック**: 保存、締め、承認、取込・再処理の開始・成功・失敗・待機を、状態ラベル、アイコン、控えめな動きで示す。処理中は二重送信を防ぐ。
- **インフォグラフィック**: 売上、前年比、客数、客単価、粗利、値引、廃棄、特売効果の表示で、棒・折れ線・構成比などのグラフを段階的に描画し、比較対象への視線を導く。
- **ダッシュボード**: 初期表示時やフィルター変更後の数値変化は、元値と新値を識別できる短い補間で示す。頻繁な自動更新で動き続ける画面にはしない。
- **状態の連続性**: 展開・折りたたみやドリルダウンは、利用者がどの店舗・営業日・集計から移動したか追える遷移にする。

## 実装・アクセシビリティ基準

- `prefers-reduced-motion`を尊重し、アニメーションの抑制・置換ができること。動きの抑制時も値、状態、操作結果は完全に同じ情報量で表示する。
- 色、動き、音だけを状態や数値の唯一の表現にしない。ラベル、数値、形状、パターン等を併用する。
- 点滅、急なズーム、視差、不要なループ、自動再生する装飾を避ける。自動更新や長い動きを停止できるようにする。
- キーボード操作、フォーカス順、フォーカス表示、スクリーンリーダー用の名称と値を保つ。グラフは要約とアクセス可能な表またはデータ一覧を提供する。
- 軸、単位、期間、対象店舗、凡例、速報/確定状態を表示する。アニメーション中も確定値と仮値を混同させない。
- 操作確認・取消が必要な金額操作では、演出が確認ステップや操作時間を邪魔しないこと。
- モーションは共通トークン（速度・イージング）で管理し、画面ごとの過剰なばらつきを防ぐ。具体値は採用UI技術の選定後に定義する。

## 検証

- モーションあり・抑制設定ありの両方で、視覚、キーボード、支援技術を確認する。
- 初回表示、フィルター変更、データ再取得、ゼロ値、欠損、エラー、通信遅延を確認する。
- 112店舗・締めピーク・想定同時利用数を踏まえ、アニメーション中に描画が重くならないか測定する。
- グラフの値が元データと一致することをテストし、色・アニメーションに依存しない読み取り手段を確認する。
- 売上、締め、承認などの主要フローは、動きなしでも同じ手順で完了できること。
