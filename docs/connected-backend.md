# PostgreSQL接続・モックDB・実操作の起動手順

## 現在の実装範囲

データアクセスを `src/domain/contracts.ts` の契約に統一し、`src/server/container.ts` で実装を選択する。現在はPGlite（既定のローカルデモ）、Supabase PostgreSQL / Auth、MySQL 8.4 / ローカル認証を選択できる。画面は各DBのSDKやテーブル名を直接扱わない。UI共通設定は `src/config/ui.ts`。

DB設定済みの画面では、DBエラーを架空データへ置き換えない。設定がない場合のプレビューは明示された別モードであり、DBへの保存や業務完了を意味しない。

これは全226要件の受入完了の宣言ではない。返品/取消・ポイントの独立した業務フロー、見切り/タイムセール、帳票の全要件、無操作時間によるセッション失効、公開後の特売変更・取消、移行/性能/復旧の受入は別途残る。既存POSが確定済みの取消/返品明細は標準取込の明細種別として受け付けるが、当システムの新規返品承認を代替しない。

## 接続設定

`DATABASE_PROVIDER` で接続先を選ぶ。未設定時はPGlite、`supabase` はSupabase、`mysql` はMySQLを使用する。秘密情報をソースや共有資料へ転記せず、ローカルではGit対象外の `.env.local` に保存する。

### MySQL 8.4

1. `.env.example` を `.env.local` へコピーし、`DATABASE_PROVIDER=mysql` を設定する。
2. `MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_DATABASE`、`MYSQL_USER`、`MYSQL_PASSWORD` を設定する。アプリはホスト・DB名・利用者を必須とし、ポートは1～65535の整数として接続前に検査する。
3. `SESSION_SECRET` に32文字以上のランダム値を設定する。これはブラウザへ公開しない。
4. 開発者所有の空DBであることを確認してから `npm run db:mysql:migrate` を実行する。架空データが必要な場合だけ `npm run db:mysql:demo` を続けて実行する。
5. `npm run dev` を起動する。アプリ本体、マイグレーション、デモ投入は同じ `MYSQL_*` 設定を使用する。

既存DBへ適用する場合は、先にDDLとデータ移行計画を照合する。既存スキーマのresetや手作業変更は行わない。

### Supabase

1. `.env.example` を `.env.local` へコピーする。
2. `NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_ANON_KEY`、サーバー専用の `SUPABASE_SERVICE_ROLE_KEY` を設定する。キーをチャットやソースへ貼らない。
3. `APP_ORIGIN` を実際のアクセス元に合わせる。ローカルの既定は `http://localhost:3000`。
4. Supabase Authに `APP_ORIGIN/auth/callback` をリダイレクト先として登録する。パスワード再設定にはメール送信設定も必要。
5. 既存CLI運用に従って対象のモック/開発プロジェクトへリンクし、`supabase db push --linked --dry-run` で版と差分を確認する。その後、モック環境に `supabase db push --linked` を実行する。

既存DBが別スキーマの場合は、そのDBをresetしたり、既存テーブルへ強制適用しない。既存DDLとの対応を確認し、アダプターの列対応または追加の互換マイグレーションを用意する。マイグレーションはGitで版管理し、Productionへの手作業変更は行わない。

接続先ごとの実環境検証結果は、資格情報を含めず [接続済みデモ環境の検証記録](./demo-connection-verification.md) に残す。自動テストは接続設定契約、MySQL DDL、端末スナップショット、PGlite上の業務統合試験を分けて実施する。

## 既存モックを使う場合

すでに格納済みのモックデータは、そのまま利用できる。Auth上のユーザーIDに一致する `app_users.id` と、有効な `user_role_assignments` が必要。業務データだけを挿入しても個人ログインはできない。アプリから管理者ユーザーを自動昇格させない。

社員情報の `email` はAuthが正本。通常売価と特売対象区分は既存マスタの参照キャッシュであり、商品編集画面で独自の正本を作らない。

## 追加の架空データが必要な場合

`.env.local` に `ALLOW_DEMO_DATA_SETUP=true` を設定し、`npm run db:demo` を実行する。Productionでは実行しない。

認証アカウントも作る場合は `DEMO_SEED_AUTH_USERS=true` と、12文字以上の `DEMO_INITIAL_PASSWORD` を環境変数へ設定する。実行結果は件数だけを表示し、パスワード/キーを表示しない。既存パスワードは更新しない。

- 3店舗、2エリア、食品/日用品/EDLP対象の架空商品、通常売価、在庫、直近の売上、当営業日の売上、特売下書き、店舗お知らせを作成する。
- Auth作成時は8ロールの別アカウントを作る。メールアドレスは `minoriya-demo+ロール名@example.invalid`。例: `minoriya-demo+information_systems@example.invalid`。
- 初回ログイン後に個人パスワードへの変更が必要。認証パスワードを実際に変更したときだけDBの変更待ちフラグを解除する。
- `.invalid` は架空ドメインなのでメールを受信できない。再設定メールまで試す場合は、管理下のテスト用メールドメインとAuthメール設定を使用する。
- 既存コード/IDは上書きせず、再実行時は同じ明細や通知を二重登録しない。予約した `FIXTURE-V1-*` のコードを別用途に転用しない。
- デモ店長の自店舗には架空の確定済み過去売上を初期化する。通常の操作で締めた実績の代替ではなく、修正承認を試すためのfixtureである。
- 特売は下書きで作成し、外部POSへの送信を自動開始しない。初期データ作成だけで実ベンダーAPIを呼ばない。

起動は `npm run dev`。情報システムの個人アカウントで管理ログインし、店舗・端末管理から閲覧用端末コードを発行する。対象PCの `/station` へ一度入力すると、店舗の通常参照は個人ログインなしで利用できる。

端末コードは発行時に一度だけ表示する。DBにはダイジェストのみを保持し、監査にもコード/ダイジェストをコピーしない。ブラウザにはHttpOnlyのセッションCookieを設定し、永続期限は独断で業務要件化しない。管理者の無効化で即時拒否する。個人ログアウトは端末の閲覧登録を解除しない。

## 外部APIを接続する場合

[外部連携契約](./integration-api.md)と[OpenAPI](./openapi.integrations.yaml)に合わせたアダプターAPIを用意する。

| 設定                                  | 用途                                              |
| ------------------------------------- | ------------------------------------------------- |
| `ERP_ORDER_API_URL` / `ERP_API_TOKEN` | 基幹への発注送信                                  |
| `POS_PRICE_API_URL` / `POS_API_TOKEN` | 既存POSへの特売適用・通常売価復帰                 |
| `INTEGRATION_INGEST_TOKEN`            | 在庫・通常売価/対象区分・売上の受信（32文字以上） |
| `CRON_SECRET`                         | 定期実行の認証（32文字以上）                      |

スケジューラーから `POST /api/integrations/run` を定期実行する。GETも対応する。ローカルからは `npm run integrations:run`。実行周期はPOSの反映方式と業務責任者の判断で設定し、未確定のSLAとして固定しない。URL/トークンがない連携種別は送信しない。

失敗はDBと通知へ残り、情報システムまたは権限保有者が連携監視で再処理できる。通常売価の参照値がない、または店舗/全店の価格が矛盾して優先順位を判断できない場合は、0円や推測した価格を送信せず失敗として残す。

## DBを変更する場合

画面の参照先を個別に修正せず、`BusinessRepository` / `IdentityProvider` / `IntegrationJobStore` を新DB向けに実装し、`src/server/container.ts` の選択を変更する。`QueryOptions`、DTO、操作結果はSupabaseクライアント型やSQLのエラー型を外へ出さない。

PostgreSQLのRPC・RLS・トリガー・ロックは、他DBにそのまま移植できない。新アダプターで原子的保存、担当範囲、無効利用者、月次確定後拒否、二段階承認、重複排除、競合更新、監査、リースを再現し、同じ契約試験を通す。DBの移行・データ照合自体が不要になるわけではない。

Supabase Authだけを継続する構成も可能。認証ユーザーIDと新DBの社員/ロールを対応付けるアダプターを用意する。ベンダー別のファイル/API形式変更は `IntegrationTransport` 側で吸収する。

MySQL管理機能（2026-10-22）: 特売の下書き作成・版番号付き編集・既存マスタの対象区分反映・公開・担当店舗の確認/売場作業、特売/価格変更指示の発行・店舗確認を原子的トランザクションで実装した。公開は対象区分と現行商品マスタを再検査し、同一商品・店舗・期間の重複を拒否する。商品行を商品ID順にロックして同じ商品の公開を直列化する（店舗別ロックより広いが競合取りこぼしを避ける）。データ・対象店舗向けお知らせ・操作者付き監査を一括保存する。外部POSへの価格送信は追加していない。個人通知は件数取得と一覧取得の双方で本人IDを必須条件とし、売上検索の店舗/エリア選択肢も担当範囲で絞る。

店舗の特売タスク（2026-10-22）: 対象店舗の担当者は `/store/notices` でPOS価格変更と商品値札変更を個別に完了登録できる。POSの完了は外部POSの自動反映結果ではなく、担当者による手動確認を `manual_confirmed` として保存する。MySQLは同一トランザクション内で担当店舗を再検査して監査ログを保存し、Supabaseは版管理マイグレーション `202610230008_store_campaign_task_confirmation.sql` で同じ認可境界を適用する。

2026-10-22 特売公開の変更依頼拡張: 公開時に既存の作業指示/対象店舗/お知らせへ商品単位のPOS・値札変更依頼を原子的に保存する。価格・開始日時・終了日時を日本時間で記載し、店舗の `/store/notices` と `/store/campaigns` で確認できる。PostgreSQLは `202610220001_campaign_change_requests.sql` で既存の公開トリガー関数を差し替え、MySQLは公開トランザクション内で同じ既存テーブルへ保存する。既存特売への過去通知の再送は行わない。
