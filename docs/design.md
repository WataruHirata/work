# 実装・レビュー設計規約

この文書は、変更の意図と影響範囲を短時間で確認できるコードを維持するための共通規約です。業務要件は[統合要件書v3](./requirements/みのり屋_販売管理システム_統合要件書_v3.md)、画面構成は[ルート設計](./routes.md)を一次資料とします。画面遷移図は再追加時に `docs/diagrams/` へ配置します。

## リファクタリングの定義

リファクタリングは、外部から観測できる振る舞い、権限判定、保存形式、画面操作の契約を変えずに、内部構造を読みやすくする変更です。名称変更、責務の分割、重複の削減、型の明確化が該当します。

要件、表示、API、DBスキーマ、権限、エラー処理のいずれかが変わる場合は、リファクタリングだけとして扱いません。対象の要件・設計・テスト・運用資料を同じ変更に含め、レビュー説明に振る舞いの差分を書きます。

## 境界と責務

| 場所                  | 担当                                    | 置かないもの                      |
| --------------------- | --------------------------------------- | --------------------------------- |
| `src/app/`            | URL、ページ合成、HTTP入口               | 業務ルール、SQL、表示部品の詳細   |
| `src/components/`     | 表示、入力、操作フィードバック          | 接続情報、権限の最終判定、直接SQL |
| `src/domain/`         | 業務用語、型、純粋な計算と判定          | Next.js、React、DBクライアント    |
| `src/server/`         | 認証・認可、入力検証、ユースケース      | ブラウザ専用の状態管理            |
| `src/infrastructure/` | DB・外部サービスへの変換                | 画面固有の表示判断                |
| `src/config/ui.ts`    | 画面名、URL、アイコンなどの共通表示設定 | 権限の実判定、業務計算、秘密情報  |
| `database/`           | スキーマ、マイグレーション、接続実装    | UI表示の文言                      |

依存は画面からサーバー、サーバーからドメインと基盤へ向けます。DBや外部サービスを差し替えるコードは `infrastructure` または `database` の境界に閉じ込めます。

## 書き方

- 1ファイルと1関数には、説明できる一つの責務を持たせます。長い条件分岐は、業務用語を表す名前の関数または定数に分けます。
- 名前は用途・対象・単位が分かるものにします。汎用名の `data`、`item`、`utils` を公開境界の名前に使いません。
- コンポーネントのprops、Server Action、リポジトリの入出力には明示した型を使います。外部入力は境界で検証してからドメインへ渡します。
- 同じ意味の表示値、URL、ラベルは `src/config/ui.ts` に集約します。権限と業務ルールはそこへ置きません。
- UIの状態と副作用は必要なコンポーネントに限定します。サーバーで完結する取得・認可をClient Componentへ持ち込みません。
- コメントは「何をしているか」ではなく、制約・判断理由・避けられない例外を説明します。古い実装の経緯は設計資料または変更履歴に残します。

## データ・権限

- 認可、店舗・エリア境界、更新可能性は必ずサーバー側で再確認します。画面の非表示だけをアクセス制御に使いません。
- SQLはパラメータを束縛し、DB固有の記法はアダプター層に閉じます。スキーマ変更は版管理されたマイグレーションで行います。
- 秘密情報は環境変数だけで扱い、コンポーネント、設定ファイル、テストfixture、ログへ書きません。

## 検査とレビュー

変更前後で、少なくとも対象範囲の `npm run format:check`、`npm run lint`、`npm run typecheck` と関連テストを実行します。画面・依存関係・ビルド設定を変更した場合は `npm run build` も実行します。

レビューでは次を確認します。

- 変更の目的、対象要件、利用者から見える振る舞いが説明されている。
- 正常系、空状態、失敗時、権限不足時の扱いが分かる。
- 権限、金額、税、承認、締め、監査、移行に影響する場合は根拠となるテストがある。
- 関係ない整形、名称変更、依存更新が混ざっていない。
- 新しい共通設定が既存の設定と重複せず、責務のある場所に置かれている。
